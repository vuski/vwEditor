# 텍스트 모드 가로 스크롤 — 줄 번호를 고정하려고 스크롤을 직접 만든 기록

**작업 범위:** `199bfe0` (1 커밋, master)
**날짜:** 2026-09-29
**릴리스:** v1.0.3

보고는 둘이었다. "기본으로 띄운 뒤 창보다 길게 입력하면 볼 방법이 없다. 가로
스크롤이 왜 안 보이나." 그리고 "End를 눌러도 화면이 그 줄 끝으로 가지 않는다."

한 번 고쳤다가 **구조를 통째로 바꿨다.** 첫 수정은 동작했지만 줄 번호가 같이
밀려났고, 사용자가 줄 번호는 고정돼야 한다고 했다. 드래그 자동 스크롤도 같은
자리에서 요청됐다.

---

## 1. 원인: 텍스트 뷰는 "한 줄은 창에 들어간다"는 전제였다

처음 띄우면 나오는 빈 문서는 **텍스트 편집 모드**다. PR #1은 표·헥스 뷰만 가로
스크롤로 감쌌고 텍스트 뷰(`render_text`)는 손대지 않았다.

- 텍스트 열이 `Column::remainder()`라서 폭이 늘 "창에 남은 폭"이었다.
- 줄은 셀 사각형으로 잘라 그렸다(`with_clip_rect(cell_rect)`). 창보다 긴 부분은
  스크롤할 공간 자체가 만들어지지 않았다.
- End는 캐럿을 줄 끝으로 정확히 옮기고 있었다(`CaretMove::End`). 화면을 캐럿
  쪽으로 옮기는 코드가 가로 방향으로 없었을 뿐이다.

두 증상은 같은 뿌리다.

## 2. 첫 시도: 표 전체를 `ScrollArea::horizontal`로 감싸기

표·헥스 뷰와 같은 구조로 맞췄다. 텍스트 열을 `Column::exact(가장 긴 줄 폭)`로
두고(`initial`은 처음 한 번만 적용되어 긴 줄을 만나도 넓어지지 않는다), 캐럿이
움직이면 `ScrollArea::horizontal_scroll_offset`으로 옮겼다. 테스트도 통과했다.

그런데 표 전체가 가로로 밀리므로 **줄 번호 열도 같이 사라졌다.** 에디터에서
줄 번호가 밀려나는 것은 받아들이기 어렵다. 표 모드의 `#` 열도 같은 이유로
밀리지만, 표는 엑셀처럼 "행 전체를 옆으로 본다"는 감각이라 덜 어색하다.

## 3. 두 번째: 가로 offset을 우리가 소유한다

`TableBuilder` 안에서 열 하나만 가로 스크롤하는 방법은 없다. 그래서 가로
스크롤을 egui에 맡기지 않았다.

- 표는 창 폭에 맞춘다(텍스트 열은 다시 `remainder` + `clip`).
- 텍스트 열 **안에서만** 글자를 `TextHScroll::offset`만큼 왼쪽으로 옮겨 그린다.

바꿔야 할 곳이 많을 것 같았지만 한 줄이었다. 편집 경로의 캐럿·선택 음영·클릭
역매핑(`pos_at_pointer`)·IME 창 위치가 전부 줄마다 같은 `origin`에서 계산된다.
`origin.x = cell_rect.left() - hoff` 하나만 바꾸면 전부 함께 따라온다. 뷰 경로
두 개(Label, 검색 중 galley)도 같은 방식으로 원점만 밀었다. 원래 있던 규율이
이 결정을 쉽게 만들었다 — "galley 하나가 그리기·char→x·x→char의 유일한
진실"(`render_text` 주석)이라 좌표 계산이 흩어져 있지 않았다.

가로 스크롤바는 텍스트 열 바로 아래에만 그린다. v1.0.2에서 만든 세로 스크롤바
코드(`20260924_PR병합과_컬럼필터_재작업.md` 5절)를
축 공용 함수 `drag_scrollbar`로 일반화해 가로·세로가 같이 쓴다. 이 함수는 상태를
갖지 않고 새 offset만 돌려준다 — 세로는 egui `ScrollArea` 상태에, 가로는
`TextHScroll`에 쓴다.

## 4. 스크롤 범위: 보인 줄만 잰다

가로 스크롤 범위는 가장 긴 줄의 폭이다. 파일 전체에서 찾으려면 전체 스캔이
필요하다. 그래서 **화면에 그려진 줄의 galley 폭 최댓값**을 쓴다. 줄마다 이미
만들고 있는 galley의 `size().x`를 읽을 뿐이라 추가 비용이 없다.

- 값은 줄어들지 않는다. 스크롤하다 짧은 구간에 오면 범위가 줄어 화면이 튀기
  때문이다. 글꼴 크기(확대 배율)가 바뀌면 다시 잰다.
- 대가: 아래쪽에 더 긴 줄이 있으면, 그 줄이 화면에 나타날 때 범위가 늘어난다.
- 캐럿 따라가기 때는 캐럿 줄의 폭을 먼저 범위에 넣는다. offset은 범위로
  클램프되므로, 안 넣으면 범위가 캐럿까지 닿지 않아 옮겨지지 않는다.

## 5. 캐럿 따라가기 규칙 (`hscroll_to_show`)

- 가장자리를 넘을 때마다 한 글자씩 밀면 타이핑 중 화면이 계속 떨린다. 넘으면
  창 폭의 1/4(`chunk`)만큼 여유를 두고 한 번에 옮긴다. 메모장과 같다.
- 왼쪽으로 넘었는데 캐럿이 첫 화면 안에 들어가면 0으로 돌아간다. Home이 줄
  맨 앞을 보여 주도록.
- **키 입력으로 캐럿이 움직였을 때만** 따라간다. 인텐트 적용 전후 캐럿을 비교해
  `follow_caret`를 세운다. 마우스 클릭은 이미 보이는 자리라 필요 없고, 우클릭
  메뉴는 선택 밖을 누르면 캐럿을 **줄 끝**으로 보내므로 따라가면 화면이 엉뚱하게
  튄다. 그래서 우클릭 처리(4단계)보다 앞, 키 인텐트(3단계) 직후에서만 비교한다.
- 인텐트는 프레임 끝에 적용되므로 실제 이동은 다음 프레임 시작에 한다.

## 6. 드래그 자동 스크롤 (가로·세로)

없던 기능이다. 세로 방향도 없었다.

- **끝점 갱신.** 예전에는 `resp.contains_pointer()`로 포인터가 올라간 줄만 끝점을
  갱신했다. 포인터가 셀 밖(창 오른쪽, 표 아래)으로 나가는 순간 갱신이 멈췄다.
  이제는 포인터를 **본문 영역 안으로 클램프**(텍스트 열 가로 범위 × 본문 세로
  범위)한 뒤 그 y가 드는 줄의 끝점으로 삼는다. 선택이 가장자리까지 이어진다.
- **스크롤 양.** `edge_autoscroll`: 가장자리 밖으로 나간 거리의 절반, 최소 2px,
  상한은 세로 3행·가로 6행 높이 분량. 멀리 나갈수록 빨라지되 한 프레임에 화면을
  건너뛰지 않는다.
- **포인터가 멈춰 있어도 굴러야 한다.** egui는 입력이 없으면 다시 그리지 않으므로,
  자동 스크롤 중에는 `request_repaint()`를 부른다.
- 세로는 표 안쪽 `ScrollArea`의 상태를 `State::load/store`로 직접 민다.

## 7. Shift+휠

egui가 Shift+휠을 가로 스크롤로 바꿔 준다(`input_state.rs`, `modifiers.shift`면
`delta = (x + y, 0)`). 표 안쪽 세로 `ScrollArea`는 **자기 축만** 소비하므로
(`always_scroll_the_only_direction`이 꺼져 있을 때) 가로 델타가 남아 있고, 표
위에 포인터가 있으면 그것을 받아 offset에 더한 뒤 소비 처리한다.

## 8. 테스트와 프로브

- `hscroll_to_show` 순수 함수 4개, `edge_autoscroll` 1개.
- `text_mode_end_key_scrolls_horizontally_and_home_returns` — 2,000자 줄에서
  End → offset > 1000, Home → 0. 실제 `egui::Context`로 프레임을 돌리고 키
  이벤트를 넣는다.
- `text_drag_past_edges_autoscrolls_both_axes` — 3,000자 × 200줄 문서에서 누른 채
  포인터를 오른쪽 밖에 멈춰 두면 offset과 선택 끝 열이 계속 늘고, 아래 밖으로
  끌면 첫 화면 밖 줄까지 선택된다.

두 통합 테스트는 **기능을 잠시 끄고 돌려 실패하는지** 확인했다(`follow_caret`을
세우지 않게 / `edge_autoscroll`이 0을 돌려주게). 각각 보고된 증상 그대로
("End 뒤 offset 0", "오른쪽 밖으로 끌어도 안 굴러감")로 실패했다. 통과만 보고
끝내면, 테스트가 정말 그 버그를 잡는지 알 수 없다.

줄 번호가 고정되어 **보이는지**는 자동 테스트로 확인하지 못했다. 사람이 봤다.

## 9. 남은 것

- 표 모드의 `#` 열은 아직 PR #1 방식(표 전체 가로 스크롤)이라 같이 밀린다.
- 표 모드 셀 드래그 선택에는 자동 스크롤이 없다.

## 작업 중 걸린 것

- **Python으로 Rust 코드를 쓸 때 `\n`.** 테스트 코드 안의 `'\n'`을 Python 문자열에
  `'\\n'`으로 적었더니 삼중 따옴표 안에서 한 번 풀려 Rust 소스에 실제 개행이
  들어갔다. 고치려고 `re.sub`에 `r"...\\n..."`을 줬더니 치환 문자열에서
  `\n`이 다시 개행으로 해석됐다. 치환 인자를 함수(`lambda m: lit`)로 넘겨서야
  글자 그대로 들어갔다.
- **실행 중인 exe.** 사용자가 앞 빌드를 띄워 둔 상태라 `target\release`를 덮어쓸
  수 없었다. 프로세스를 끄지 않고 `--target-dir target\trial`로 확인용 빌드를
  따로 만들었다. 배포 빌드는 확인 뒤 `build-release.ps1`로 다시 만들었다.
